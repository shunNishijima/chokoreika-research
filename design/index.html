2. 報告書タブ（/admin/report）

行政・協賛企業に渡す A4 縦の印刷・PDF 用。画面: app/web/src/admin/Report.tsx、集計: app/server/src/domain/report.ts（ダッシュボードの集計 metrics.ts と一緒に GET /api/admin/report で返す）。

操作

  • 期間: 全期間 / 今年度（4月始まり）/ 直近6か月 / 直近3か月
  • 外部共有モード（5人未満を隠す）: 既定でオン。オフにすると画面に「外に出す資料ではオンに」の注意が出て、印刷の定義欄も「内部用」の文言になる
  • 題名・団体名・運営からのひとことは、その端末のブラウザに覚えておく（サーバーには保存しない）
  • 「印刷・PDF に保存」でブラウザの印刷。ページごとに改ページする

構成（印刷のページ順）

  1. 表紙と要約: 題名・団体名・対象期間・作成日、主要な数字8つ（開催した回数・延べ参加・実人数・はじめて来た人・もう一度来た人の割合・1人あたりの参加回数・1回あたりの参加・滞在時間の中央値）、自動で作る「まとめ」の文章、運営からのひとこと
  2. 参加の推移（月ごと）: 延べ参加（はじめて / 2回目以上）の積み上げ棒と実人数の線、月ごとの表。会の種類・主催（老人会）ごとの開催回数・延べ参加・1回あたり
  3. どんな人が来ているか: 年齢層・性別、非会員・一人暮らし・杖や手押し車などで来た人の割合、担い手の人数。気分の変化（良くなった / 変わらない / 下がった人の割合、平均の変化、来たとき・帰るときの分布）
  4. どこから来ているか: 大阪府の市町村地図（実人数）。市町村が分かる人がいないときはこのページを出さない
  5. 数字の出し方と個人情報の扱い

報告書だけの指標の定義（コードから）

指標計算
月ごとの推移期間内の会がある月ごとに、開催回数・延べ参加・実人数・はじめて来た人（全期間で最初の出席がその会の人）
もう一度来た人の割合（再来率）期間中にはじめて来た人のうち、その後の日付の会にも来た人の割合。後の会は期間外でも数える。期間の終わりごろに初めて来た人は低めに出る
滞在時間受付時刻〜退出時刻（分）。退出を記録した出席だけで、5分未満（押し間違い）と12時間超（退出の押し忘れ）を除く。平均と中央値を出し、表紙には中央値を載せる
年齢層同意した人（実人数）だけ。生まれ年があれば「作成日の年 − 生まれ年」で 65歳未満 / 65〜74歳（前期高齢者）/ 75〜84歳 / 85歳以上 に分ける（誕生日前の人は1歳多くなりうる）。生まれ年がなければ標準の受付で選んだ年代、どちらもなければ未回答
会の種類・主催ごと会の kind / host ごとの開催回数・延べ参加・1回あたり（小数1桁）。主催が空なら「（未設定）」
まとめの文章数字から自動で作る。来たときの気分で「いい」「すごくいい」の割合、両方答えた人の気分の平均（来たとき → 帰るとき）を含む

そのほかの数字（実人数・はじめて・非会員・一人暮らし・担い手・気分の変化・市町村）はダッシュボードと同じ計算（定義はサービス設計タブの「ダッシュボードの指標」）。

5人未満を隠す範囲

隠すのは、年齢層・性別の内訳と市町村地図のうち 5人未満の区分（「—」・斜線）。主要な数字、月ごとの表、会の種類・主催ごとの表、気分の分布は人数が少なくても隠さない。

3. API 一覧と認証

定義: app/server/src/http/app.ts（受付・管理）、auth.ts（ログイン）。すべて JSON。

認証のしくみ

方式誰が使う中身
端末 Cookie受付の iPad受付の合言葉を一度入れると、署名付き Cookie（180日）を渡す。合言葉を変えると古い端末は使えなくなる。5回まちがえるとその接続元は5分待ち
受付トークンQR から開いた端末会ごとのランダムな文字列。管理画面「開催」の QR（/kiosk?e=会ID&t=トークン）で開くと、その会だけ受付できる（x-kiosk-token ヘッダー）
試用モード全員環境変数 ADMIN_AUTH=none。管理画面がログインなしになり、受付も端末登録なしで使え、受付画面からその日の会を作れる
Google ログイン運営Google の ID トークンを検証し、許可リスト（ADMIN_EMAILS）のメールだけ署名付き Cookie（8時間）を渡す。OAuth クライアント ID は GOOGLE_CLIENT_ID

受付用（/api/kiosk/…）

メソッドとパス何をする必要な認証
POST /api/kiosk/device合言葉を確かめて端末を登録合言葉

POST /api/kiosk/events/:id/checkoutID で退出（結果: ok / not-checked-in / unknown）同上

5. 注意点と未定事項

コードを読んで分かった注意点

  • ID が 5桁になる問題: ID は「今ある最大の番号 + 1」を 4桁にゼロ埋めして作る（同時登録でぶつかったら最大5回取り直す）。9999人を超えると 10000 のような 5桁になるが、受付の ID 入力は 1〜4桁しか受け付けないため、その人は ID で受付・退出できない。また番号の最大値を文字列として比べているため、5桁が混ざると次の番号が正しく作れないおそれがある
  • ネコ受付の退出では帰りの気分を取らない: 退出の API に気分を送らないため、帰るときの気分は空になる。気分の変化（来たとき → 帰るとき）は標準の受付で退出した人だけで計算される
  • 試用モードでは受付も端末登録が要らない: ADMIN_AUTH=none にすると管理画面だけでなく受付も合言葉なしで使え、POST /api/kiosk/events で誰でもその日の会を作れる（入力した老人会名は選択肢にも加わる）
  • 参加者 CSV に生まれ年が入る: CSV に名前は含めないが、生まれ年は含む（年代・性別・市町村・老人会なども入る）。外に渡すときは注意
  • 報告書で隠さない数字がある: 月ごとの表・会の種類/主催ごとの表・気分の分布は、外部共有モードでも5人未満を隠さない（2.）
  • 合言葉の入力失敗の制限はサーバーのメモリ上: 5回まちがえると5分待ちになるが、記録はインスタンスごとのメモリにあり、再起動や別インスタンスでは数え直しになる

未定事項（コードからは分からない・決まっていない）

  • 未定 9999人を超えたときの ID の扱い
  • 未定 ネコ受付でも帰りの気分を取るか
  • 未定 個人情報の保存期間と、本人からの削除の依頼への対応（参加者を1人だけ消す画面・API は今はない。出席の取り消しはできる）
  • 未定 DB のバックアップの方針、月々の費用
  • 未定 旧試作（choko-reception）の公開 URL と、今も使うかどうか
  • 認証方式・受付の種類・年代と生まれ年の扱いなどは、サービス設計タブの「決めていないこと」を参照
